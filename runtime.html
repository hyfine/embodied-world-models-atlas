WM-1 / Latent dynamics & model-based RL

PlaNet

Prediction / decision mechanism

Both learn latent dynamics. PlaNet compares actions at decision time; Dreamer uses imagined rollouts to train an actor.

  • PlaNet — search at decision time
  • Dreamer — imagination during training
Read the steps as text
  1. Camera frame and previous action
  2. RSSM filters the current state
  3. CEM samples action sequences
  4. Roll out latents and sum predicted rewards
  5. Refit the distribution to high-return sequences
  6. Planner sends only the first action to the environment

Feedback & boundary. After execution, filter with the new environment image and replan; imagined frames are not measurements.

Evidence test. Six simulated pixel-control tasks; Fig. 4 separates search from data collection. Planning with true dynamics is a comparator, not a deployment input.

Primary source · §§2–3, Algorithms 1–2, Fig. 4, Table 1; Appendix D Fig. 7 · Full reading note

WM-2 / Predictive representations

V-JEPA 2-AC

State representation

I-JEPA is a representation precursor, not an action-transition model. Robot interaction and a separate planner give 2-AC a control interface.

  • I-JEPA — image representation objective
  • V-JEPA 2-AC — action-conditioned prediction for planning
Read the steps as text
  1. Read camera image, goal image and end-effector state
  2. Frozen encoder embeds current and goal images
  3. CEM proposes end-effector commands
  4. Action-conditioned predictor rolls out patch features
  5. Rank and refine candidates by terminal L1 goal distance
  6. Planner sends the first command to the arm

Feedback & boundary. Read the physical camera and arm state after execution; pick-and-place switches supplied goal images on a fixed schedule.

Evidence test. Table 2: ten trials per task per lab; mean cup/box grasp rates are 65%/25%. Figure 16 shows sensitivity to camera position.

Primary source · §§3–4, Figs. 6–7, 10, 16; Tables 2–3 · Full reading note

WM-3 / Interactive video worlds

Genie

Prediction / decision mechanism

Both produce interactive futures. The control signal differs; playable transitions do not establish a calibrated robot interface.

  • Genie — latent actions inferred from video
  • GameNGen — frames conditioned on game actions
Read the steps as text
  1. Encode the prompt image as discrete visual tokens
  2. Player selects a latent action code
  3. Spatiotemporal dynamics fills next-frame tokens given history and action
  4. Visual decoder renders the frame for the player
  5. Append generated tokens to history and await the next input

Feedback & boundary. Feedback is generated history plus player input, not an external sensor. The training-time action inference network is absent during play.

Evidence test. On platformers pixel-input action inference raises ΔPSNR from 1.33 to 1.91 while FVD worsens from 38.8 to 40.1; memory is 16 frames and runtime about 1 FPS.

Primary source · §§2.1–2.2 Figs. 4–7; §3.4 Table 2; §5 · Full reading note

WM-4 / Spatial scene representations & change

WonderWorld

State representation

These exemplify geometry and consistent rendering. Seeing the same object after moving the camera is not predicting its response to a push.

  • WonderWorld — persistent layered scene
  • GEN3C — camera trajectory and 3D cache
  • OccWorld — time-varying occupancy contrast, indexed in WM-5
Read the steps as text
  1. Initialize three scene layers from one image
  2. User supplies new camera pose and prompt
  3. Render known regions and outpaint a new image
  4. Guide depth by overlap and fit layered surfels
  5. Append geometry and render it to the user

Feedback & boundary. The user chooses the next pose after seeing the result. Geometry persists; no robot policy acts.

Evidence test. 9.5 s per scene extension on one A6000, not per frame; back surfaces are not generated.

Primary source · §§3.1–3.2, 4–5; Figs. 2, 4; Table 1; App. B Algorithm 1 and App. E Table 6 · Full reading note

WM-5 / Driving scene generation & predictive planning

MagicDrive

Task / embodiment

Generating driving scenes and selecting a trajectory are distinct. Drive-WM Fig. 5 and Tables 3–4 score branches; nuScenes planning metrics are not closed-loop road-safety trials.

  • MagicDrive — conditional street views and augmentation
  • Drive-WM — forecast branches used in planning
Read the steps as text
  1. Supply a road map, 3D boxes, cameras and text
  2. Encode map features separately from scene and object tokens
  3. Denoise iteratively, exchanging adjacent-view features
  4. Decode six street views for offline testing or augmentation

Feedback & boundary. Data or a user specifies the conditions. No driver emits actions; detector outputs do not update the next observation.

Evidence test. nuScenes camera-only BEVFusion mAP rises 32.88→35.40 at 1× training but gains only 0.25 at 2×; not a driving safety test.

Primary source · §§3–4.3, 5.1–5.2; Figs. 3–4; Table 2; App. F Table 6 · Full reading note

WM-6 / Coupling robot futures to actions

DreamZero

Future–action coupling

Use both action paths. SuSIE is a cascade, not a stand-in for joint generation; video features or synthetic training data alone do not make a WAM.

  • DreamZero — joint futures and actions
  • SuSIE — subgoal image → goal-conditioned policy
Read the steps as text
  1. Observation, instruction, state
  2. Temporal generative backbone
  3. Paired outputs: future ∥ action
  4. Execute action → real feedback

Feedback & boundary. At inference, condition the next chunk on history and new observations; actions go to execution and predicted video serves modeling or inspection. This is not explicit MPC over competing videos. Count generation, communication and actuation latency separately.

Evidence test. Separate AgiBot from DROID/Franka and task progress from whole-episode success before comparing baselines. A public DROID checkpoint does not reproduce the weights, data or outcomes of a different embodiment.

EAI-1 / Language and grounded planning

ReKep

Action interface

Retain the common planning question, not a common output: constraints versus available skills. Neither directly decodes language into motor commands.

  • ReKep — generate constraints then solve
  • SayCan — language score × skill feasibility
Read the steps as text
  1. Propose 3-D keypoints from the RGB-D scene and mark their IDs on the image
  2. Condition the VLM on the instruction and marked image to write stage-end and path constraints
  3. Read current keypoints and arm state; backtrack a stage if a path constraint is violated
  4. The subgoal solver chooses an end-effector pose; the path solver finds motions to reach it
  5. Execute a prefix of the path through the low-level arm controller

Feedback & boundary. After motion, update keypoints and solve again; no fresh VLM query is required at each control step. The public simulator supplies tracking and collision geometry that physical robots must estimate.

Evidence test. Table 1: automatic constraints succeeded in 31/70 trials across seven tasks; human annotations in 48/70. Table 2 tests a different, disturbed three-task subset: 8/30 for automatic constraints.

Primary source · §§3.1–3.4, Fig. 2; §4.1, Tables 1–2; Appendix A.1 · Full reading note

EAI-2 / Vision-language-action policies

OpenVLA

Action interface

VLA names an interface, not a token format. Continuous versus discrete actions and the length of an action chunk are independent choices.

  • OpenVLA — autoregressive action tokens
  • π0 — continuous chunks with flow matching
Read the steps as text
  1. Read the current camera image and natural-language instruction
  2. Concatenate DINOv2 and SigLIP patch features and project them into the language embedding space
  3. Condition Llama 2 on vision and the instruction; autoregressively generate action-coordinate tokens
  4. Decode to bin centers and restore action scale with target-dataset quantiles
  5. Execute one end-effector and gripper command, then acquire the next image

Feedback & boundary. Demonstrations train the policy offline. The Bridge loop refreshes observations between actions; the base model takes a single image per query, does not predict future images and does not update weights online.

Evidence test. BridgeData V2: mean score 70.6% in 170 trials per policy, with partial credit on some tasks, versus 50.6% for RT-2-X. RT-2-X did better on the semantic subset; the result does not establish transfer to arbitrary new embodiments.

Primary source · §§3.1–3.3, Fig. 2; §5.1, Figs. 3–4; Appendix B.1–B.2, Tables 4 and 6 · Full reading note

EAI-3 / Visuomotor policies & demonstration interfaces

Diffusion Policy

Action interface

Start with Diffusion Policy for the action distribution, UMI for acquisition and timing. UMI deploys a policy; a gripper, coordinate frame and aligned clock are not a new policy head.

  • Diffusion Policy — policy: generate action sequences
  • UMI — demonstration and deployment interface
Read the steps as text
  1. Observations (+ task)
  2. Encode conditioning
  3. Generate action chunk
  4. Execute prefix → observe

Feedback & boundary. Iterate scheduler.step from a noisy trajectory. predict_action unnormalizes the sampled sequence and returns a slice beginning at To−1 of length n_action_steps for execution before refreshing observations. Predicted and open-loop execution horizons are different.

Evidence test. The original study evaluates action policies on 12 tasks across four manipulation benchmarks, not video prediction. Successful control is not evidence of an explicit internal cup simulator. Match execution rates and demonstration distributions before comparing methods.

EAI-4 / Trajectory data, cross-robot pretraining & adaptation

Octo

Data / transfer

Separate data collection, shared training and target adaptation. A shared format does not align actions, and transfer to a new room is not transfer to a new arm.

  • Open X-Embodiment / RT-X — pooled data and training mixture
  • Octo — policy trained on cross-robot trajectories
  • DROID — many sites with standardized hardware
Read the steps as text
  1. Tokenize the language or image goal and recent robot observations
  2. Mask unavailable inputs and compute readout tokens in the shared transformer
  3. A small diffusion head denoises an action chunk conditioned on the readout
  4. Map actions to the robot interface, execute a portion, then observe again

Feedback & boundary. Re-query on a rolling observation window; denoising iterations are not sensor feedback. New sensor/action heads are adapted offline.

Evidence test. Fig. 4 tests represented interfaces; Table I fine-tunes with about 100 target demonstrations per domain and evaluates 20 trials per domain.

Primary source · §III-A–C, Fig. 1; §IV, Fig. 4, Tables I–II; App. F · Full reading note

EAI-5 / Legged & humanoid control

Rapid Motor Adaptation (RMA)

Task / embodiment

Retain this as a body/control domain. History-based context estimation for a quadruped cannot stand in for humanoid teleoperation and whole-body imitation.

  • RMA — quadruped adaptation
  • HumanPlus — humanoid tracking and imitation
Read the steps as text
  1. Read joints, body tilt and foot contacts; retain state/action history
  2. Slow adaptor estimates a context latent from 50 history steps (about 10 Hz)
  3. Base policy reads current state, previous action and latest latent (100 Hz)
  4. Output 12 joint-angle targets; PD control converts them into torques

Feedback & boundary. The fast loop reads new state without waiting for the slow thread. No true friction input or online weight updates.

Evidence test. The 15 cm step-down succeeded in 4/5 physical trials. Table II averages simulated runs over three seeds; proprioception cannot preview a drop.

Primary source · §III-A–C, Fig. 1; §§IV–V, Fig. 2, Tables I–II · Full reading note

EAI-6 / Navigation & mobile manipulation

OK-Robot

Task / embodiment

Reaching an object and manipulating it are different success events. A grasp or release can fail after successful navigation.

  • VLMaps — semantic mapping and navigation
  • OK-Robot — navigation followed by pick-and-place
Read the steps as text
  1. Setup: manually scan posed RGB-D and build semantic and obstacle maps
  2. Retrieve the object by text and navigate the base to an approach pose with A*
  3. Filter AnyGrasp proposals with a target mask in live RGB-D; execute the grasp
  4. Retrieve the destination, navigate, then compute a drop point from its current segmented cloud
  5. Move the arm and release

Feedback & boundary. Grasp and drop use fresh local perception, not a continuously updated semantic map or a general failure-retry loop.

Evidence test. 171 trials across ten homes; 58.5% in original conditions versus 82.4% after cleanup/disambiguation, a changed test distribution.

Primary source · §II-A–D, Figs. 2–3; §III-A–D, Figs. 4–6; §V · Full reading note

EAI-7 / Simulators & evaluation

CALVIN (long-horizon language control)

Experimental infrastructure

A platform supplies transitions, a benchmark defines success, and calibration checks whether simulation ranks physical policies correctly. CALVIN alone covers only the benchmark role.

  • Habitat — simulation platform
  • CALVIN — task chains and success oracle
  • SIMPLER — paired sim/real calibration
Read the steps as text
  1. Start a feasible five-subtask chain
  2. Condition the policy on the current instruction and sensor observation
  3. Tested policy emits arm and gripper actions
  4. Simulator executes and returns new observation and state
  5. Task oracle gates retries and instruction changes; timeout ends the chain

Feedback & boundary. The next action uses fresh observations. Only success advances the instruction; timeout truncates the chain. No policy updates in evaluation.

Evidence test. 1,000 feasible five-task chains. Prefix success and mean length differ; specify scene split and sensors. This is not a real-robot test.

Primary source · §III-C2, Figs. 5, 7–8; §IV-A; §V · Full reading note

EAI-8 / RL post-training

SERL (real-world online training)

Learning stage

Online RL does not require a pretrained foundation policy. SERL teaches replay and asynchronous learning; RECAP Algorithm 1 uses experience and corrections to improve an existing VLA.

  • SERL — online real-robot RL system
  • RECAP / π*0.6 — experience-based VLA post-training
Read the steps as text
  1. Wrist images and robot state
  2. Actor policy outputs a set-point
  3. Low-level controller tracks the target; the physical robot returns a new observation
  4. Task reward and transition enter online replay
  5. Learner mixes replay with demonstrations and updates policy and critic

Feedback & boundary. Physical observations close the control loop; the asynchronous learner sends updated weights. No imagined transition or mandatory per-step human correction.

Evidence test. 100 trials per Franka task on three tasks. RL uses 20 demonstrations plus interaction versus BC on 100 demonstrations; these are not matched real-world costs.

Primary source · §§4.1–4.5, Figs. 2, 4; §5, Figs. 6–7 · Full reading note

SURVEY / Survey lenses

Li et al., A Comprehensive Survey on World Models for Embodied AI

Evidence lens

A survey is a lens, not an executable system. Use Li for design, a VLA lens for action interfaces, and Yao for what the experiment supports.

  • Li et al. — locate design coordinates
  • Ma et al. — identify VLA components and interfaces
  • Yao et al. — audit capability claims
Read the steps as text
  1. Identify the primary method, prediction target and conditioning
  2. Classify decision coupling, temporal reasoning and spatial representation
  3. Identify who selects actions: controller, policy, or no executor
  4. Select the task-specific table and trace metrics and protocol to the experiment

Feedback & boundary. This is an evidence-reading workflow, not model inference. If the primary study has no closed-loop test, record that gap instead of inventing feedback.

Evidence test. Table V occupancy mIoU, Table VI DMC returns and Table VII RLBench success cannot form a common ranking; some returns are approximated from curves.

Primary source · Fig. 1, §III; §V, Tables IV–VII · Full reading note
